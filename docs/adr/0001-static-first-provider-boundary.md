# ADR-0001: MVP는 정적 페이지로 배포하고 공급자 경계를 둔다

- 상태: 제안됨
- 작성일: 2026-07-22
- 결정 검토 시점: 첫 운영 배포 전

## 맥락

제품은 도시 검색, 기온·체감 온도·강수·UV, PM2.5·PM10 데이터가 필요하다. 초기 트래픽과 운영 요구가 확정되지 않은 상태에서 BFF를 먼저 만들면 서버 배포, 모니터링, 캐시 운영 비용이 제품 검증보다 앞선다.

초기 공급자 후보인 Open-Meteo는 공개 웹 API를 제공하므로, 최신 CORS 정책과 이용 약관 및 호출 한도가 실제 배포 용도에 맞는다면 브라우저에서 직접 조회하는 정적 애플리케이션으로 MVP를 구성할 수 있다. 다만 React 컴포넌트가 공급자 응답에 직접 결합되면 향후 공급자 변경이나 BFF 도입이 어려워진다.

## 결정

1. MVP의 React 빌드 산출물을 CDN 또는 정적 호스팅에 배포한다.
2. 브라우저의 공급자 클라이언트가 Open-Meteo의 geocoding, forecast, air-quality API를 직접 호출한다.
3. 공급자 클라이언트와 어댑터는 `services` 경계 안에 두고 외부 응답을 제품 내부 모델로 정규화한다.
4. UI와 추천 정책은 공급자 URL, 인증 방식, 고유 필드명을 알지 못한다.
5. 비밀 키를 정적 번들 또는 프런트엔드 환경 변수에 저장하지 않는다.
6. CORS, 약관, 사용량, 중앙 캐시 또는 관측성 요구가 바뀌면 동일한 내부 계약을 제공하는 BFF로 서비스 구현을 교체한다.
7. 기존 React/JavaScript 기반은 첫 수직 기능 구현 동안 유지한다.

이 결정은 실제 브라우저 smoke test와 공급자의 최신 공식 문서 및 약관 검토를 통과하는 것을 전제로 한다.

구체적인 필드 대응, 데이터 의미, 출시 차단 조건은 [Open-Meteo 요구사항 적합성 평가](../open-meteo-evaluation.md)를 따른다. 해당 문서의 승인 체크리스트가 완료되기 전에는 공급자 선택을 승인된 것으로 간주하지 않는다.

## 고려한 대안

### 처음부터 BFF/serverless function 사용

- 장점: 비밀 키 보호, 중앙 캐시와 rate limit, 공급자 은닉 및 서버 관측성이 가능하다.
- 단점: 현재 MVP에는 비밀 키 요구가 확정되지 않았는데도 배포·운영 경로와 장애 지점이 늘어난다.
- 결론: 전환 조건이 발생할 때 도입한다. 어댑터 경계로 전환 비용은 미리 낮춘다.

### React 컴포넌트에서 공급자 직접 호출

- 장점: 구현 파일과 추상화가 가장 적다.
- 단점: 외부 필드와 오류 형식이 화면 및 추천 규칙에 퍼지고 테스트와 공급자 교체가 어렵다.
- 결론: 정적 배포 여부와 무관하게 선택하지 않는다.

### 복수 공급자를 처음부터 동시 사용

- 장점: 데이터 공백과 단일 장애 지점을 줄일 수 있다.
- 단점: 관측 시각, 좌표, 단위, 모델 차이를 조정하는 복잡도가 MVP에 비해 크다.
- 결론: 어댑터 경계는 준비하되 최초 구현은 단일 공급자로 제한한다.

## 결과

### 긍정적 결과

- 서버 없이 정적 파일만 배포할 수 있어 MVP의 비용과 운영 범위가 작다.
- UI 및 추천 규칙과 공급자 응답이 분리된다.
- BFF 또는 다른 공급자로 전환할 때 `services` 바깥의 변경을 최소화할 수 있다.

### 비용과 위험

- CORS와 공급자 가용성에 브라우저 실행이 직접 의존한다.
- 사용자 간 공유 캐시, 중앙 rate limit, 서버 측 fallback을 제공하지 못한다.
- 요청 URL과 응답이 브라우저에서 보이므로 비밀 자격 증명을 사용할 수 없다.
- 외부 공급자마다 콘텐츠 보안 정책(CSP)의 `connect-src` 허용이 필요하다.
- 무료 또는 무인증 공급자라도 약관과 한도 변경을 지속해서 확인해야 한다.

## BFF 전환 조건

다음 중 하나라도 충족되면 이 결정을 검토한다.

- 공급자 인증에 비밀 키나 요청 서명이 필요하다.
- 브라우저 CORS 호출이 차단된다.
- 호출량 절감을 위한 사용자 간 공유 캐시가 필요하다.
- 남용 방지를 위한 중앙 rate limit 또는 공급자 fallback이 필요하다.
- 서버 기준 SLA, 오류율, 지연 시간 관측이 필요하다.
- 공급자 약관이 브라우저 직접 호출을 허용하지 않는다.

## 검증 과제

- 실제 대상 도시 표본으로 geocoding 품질과 동명 도시 결과를 확인한다.
- 배포 도메인과 로컬 브라우저에서 세 API의 preflight/CORS 동작을 확인한다.
- 필요한 필드, 단위, 시간대, 갱신 간격을 fixture로 기록한다.
- 예상 사용자 수로 클라이언트 호출량을 계산하고 공급자 한도와 비교한다.
- 정적 호스팅의 CSP, 보안 헤더, SPA fallback 및 캐시 설정을 확인한다.
- 배포 전 최신 공식 문서와 약관을 확인하고 이 ADR을 `승인됨`, `수정됨`, `대체됨` 중 하나로 갱신한다.
