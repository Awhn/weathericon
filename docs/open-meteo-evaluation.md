# Open-Meteo 요구사항 적합성 평가

- 평가 결론: **MVP 기능에는 조건부 적합**
- 평가일: 2026-07-22
- 승인 상태: 공식 문서·약관 및 실제 브라우저 호출 검증 전

## 1. 요약

Open-Meteo가 문서화한 geocoding, forecast, air-quality API의 필드 구성을 기준으로 보면 도시 검색, 기온·체감 온도, 강수, UV, PM2.5 및 PM10이라는 MVP 입력을 한 공급자 계열에서 얻을 수 있다. 따라서 기능 프로토타입의 우선 공급자로 적합하다.

하지만 **API가 필요한 숫자를 반환한다는 것과 운영 요구사항을 모두 만족한다는 것은 다르다.** 정적 페이지 배포에는 CORS, 공개 접근 방식, 사용량 한도, 라이선스·저작자 표시, 상업적 사용 조건을 확인해야 한다. 또한 제공 값은 관측소 실측치가 아니라 예보·대기질 모델 값일 수 있으므로 UI에서 단순히 `현재 관측`이라고 표기하면 안 된다.

## 2. 요구사항별 판정

| 제품 요구사항 | 사용할 API/필드 후보 | 판정 | 구현 시 주의점 |
| --- | --- | --- | --- |
| 도시명으로 위치 찾기 | Geocoding API의 검색 결과, 위도·경도·시간대 | 충족 예상 | 한글 검색 품질, 동명 도시 순서, 국가/행정구역 표시를 도시 표본으로 검증한다. |
| 현재 기온 | Forecast API의 `temperature_2m` | 충족 예상 | 요청한 시간대와 `current`/시간별 데이터의 기준 시각을 보존한다. |
| 체감 온도 | Forecast API의 `apparent_temperature` | 충족 예상 | 추천 규칙은 실제 기온보다 이 값을 우선하되 누락 시 판정 불가로 처리한다. |
| 현재 강수 | Forecast API의 `precipitation`, `rain`, weather code 후보 | 충족 예상 | 강수량과 강수 여부를 혼동하지 않고 단위를 응답과 함께 검증한다. |
| 향후 3시간 강수확률 | Forecast API의 시간별 `precipitation_probability` | 충족 예상 | 현재 지역 시간부터 연속 3개 시간 구간을 선택하고 누락값을 처리한다. |
| UV | 시간별 `uv_index` 또는 일별 `uv_index_max` 후보 | 부분 충족 | `현재 UV`와 `오늘 최대 UV`는 의미가 다르므로 출시 전에 하나를 제품 기준으로 확정한다. |
| PM2.5 | Air Quality API의 `pm2_5` | 충족 예상 | 모델 데이터의 기준 시각, 단위, 갱신 주기 및 지역 커버리지를 확인한다. |
| PM10 | Air Quality API의 `pm10` | 충족 예상 | 지역 보건 기준과 공급자 수치를 혼동하지 않고 출처를 표시한다. |
| 한국어 UI | 내부 번역 및 표시 모델 | 자체 충족 | 공급자 설명 문자열에 의존하지 않고 앱이 레이블과 권고 이유를 생성한다. |
| 정적 페이지 직접 호출 | 세 API에 대한 브라우저 `fetch` | 검증 필요 | 배포 origin에서 CORS가 허용되는지 실제 브라우저 smoke test가 필요하다. |
| 비밀 키 없는 배포 | 공개 접근 엔드포인트 후보 | 검증 필요 | 무료/공개 접근 조건과 실제 서비스 용도를 약관과 대조한다. 키가 필요하면 BFF로 전환한다. |
| 운영 호출량 | 공급자 사용량 정책 | 검증 필요 | 사용자 1회 검색당 최대 3회 호출을 기준으로 일·월 요청량을 산정한다. |
| 저작자 표시/라이선스 | 공급자 및 원천 데이터별 조건 | 검증 필요 | 결과 화면과 서비스 정보 화면에 필요한 attribution을 구현한다. |

`충족 예상`은 필드 수준의 기술 적합성을 의미하며 운영 승인을 뜻하지 않는다. 공식 문서에서 필드명·단위·가용성이 확인되고 fixture 및 브라우저 테스트가 통과해야 `충족`으로 바꾼다.

## 3. 권장 요청 구성

정확한 URL은 최신 공식 문서 확인 후 코드 상수로 확정한다. 어댑터가 필요로 하는 최소 데이터 집합은 다음과 같다.

```text
Geocoding
  input: city, language=ko
  output: name, admin1, country, latitude, longitude, timezone

Forecast
  input: latitude, longitude, timezone
  current/hourly: temperature_2m, apparent_temperature,
                  precipitation, precipitation_probability, uv_index

Air quality
  input: latitude, longitude, timezone
  current/hourly: pm2_5, pm10
```

위치 검색 후 forecast와 air-quality 요청은 서로 독립적으로 병렬 실행한다. 한쪽이 실패해도 다른 쪽의 추천은 표시하며, 요청 시간 제한과 `AbortController`를 적용한다.

## 4. 제품상 중요한 차이

### 현재값, 예보값, 관측값

Open-Meteo라는 공급자 이름만으로 값의 성격을 `실시간 관측`이라고 단정하지 않는다. 내부 모델과 UI는 다음을 구분해야 한다.

- `reportedAt`: 공급자가 데이터에 부여한 기준 시각
- `fetchedAt`: 브라우저가 응답을 받은 시각
- `dataKind`: `forecast`, `modelled`, `observed` 중 확인된 값
- `source`: 공급자 및 필요한 경우 원천 모델

확인 전에는 UI 문구를 `현재 관측`이 아니라 `현재 날씨 데이터` 또는 `예보 기준`으로 표현한다.

### UV 선택

외출 준비에는 `현재 UV`보다 외출 시간대 또는 오늘의 최대 UV가 더 유용할 수 있다. MVP에서 쿼리 파라미터로 외출 시각을 받지 않으므로 다음 중 하나를 명시적으로 선택해야 한다.

1. 조회 시각의 시간별 UV를 사용한다.
2. 향후 3시간 최대 UV를 사용한다.
3. 오늘의 최대 UV를 사용하고 아이콘 이유에 `오늘 최대`라고 표시한다.

초기 권고안은 우산과 같은 시간 창을 사용할 수 있도록 **향후 3시간 최대 UV**이며, 제품 검토 후 규칙 버전에 기록한다.

## 5. 정적 페이지 출시 차단 조건

다음 중 하나라도 확인되면 브라우저 직접 호출 방식으로 출시하지 않는다.

- 배포 origin에서 하나 이상의 필수 API가 CORS 오류를 반환한다.
- 서비스 용도에 비밀 키 또는 노출하면 안 되는 자격 증명이 필요하다.
- 예상 호출량이 허용 한도를 넘고 클라이언트 캐시로 해결할 수 없다.
- 상업적 사용 또는 저작자 표시 조건을 서비스가 준수할 수 없다.
- 대상 지역에서 UV 또는 미세먼지 필드가 지속적으로 누락된다.
- 공급자 데이터의 성격과 갱신 시각을 사용자에게 정확히 설명할 수 없다.

이 경우 `services`의 내부 반환 형식은 유지하고 Open-Meteo 호출만 BFF 또는 다른 공급자 어댑터로 교체한다.

## 6. 승인 체크리스트

- [ ] 공식 Forecast API 문서에서 필요한 필드, 단위, 시간 해석을 확인했다.
- [ ] 공식 Air Quality API 문서에서 PM2.5, PM10, UV 제공 위치를 확인했다.
- [ ] 공식 Geocoding API 문서에서 검색 파라미터와 attribution 조건을 확인했다.
- [ ] 최신 이용 약관에서 비상업/상업 용도, 호출 한도, attribution을 확인했다.
- [ ] 로컬 및 실제 배포 origin에서 세 API의 브라우저 호출을 확인했다.
- [ ] 서울, 부산, 제주와 해외 동명 도시를 포함한 fixture를 저장했다.
- [ ] 일부 응답 실패, null 필드, 시간 초과, 오래된 응답을 테스트했다.
- [ ] 예상 사용자 수 × 검색당 호출 수로 월간 호출량을 산정했다.

체크리스트 완료 전 결론은 `조건부 적합`이며, 완료 후 결과와 확인한 공식 문서 버전/URL을 이 문서에 기록한다.
